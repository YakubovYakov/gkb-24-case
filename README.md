# Сайт ГКБ № 24: разбор проекта

Публичный сайт московской городской клинической больницы № 24: [gkb-24.ru](https://gkb-24.ru). Страницы врачей и отделений, прайс, новости, запись на приём, админ-панель для сотрудников. Работаю над проектом с ноября 2024 года: разработка, поддержка в продакшене, SEO.

Код закрытый, это рабочий проект больницы. Здесь описано, как он устроен и какие решения принимались. Данные на 9 октября 2026 года.

## Архитектура

```
Браузер, поисковый робот
          |
        Nginx        TLS, редиректы www -> без www, раздача загруженных файлов
       /      \
 Next.js        Express API ---- PostgreSQL
 (SSR)               |
                     +--------- Redis (кэш списков)
```

- Страницы рендерятся на сервере и сами ходят в API: поисковый робот получает готовый HTML.
- Основной сайт и версия на поддомене живут в одном приложении. Маршрутизация по имени хоста, общие компоненты, отдельные макеты и страницы.
- Данные врачей фильтруются на стороне бэкенда, список врачей кэшируется в Redis и сбрасывается при любой правке.

## Инженерные решения

### 1. SEO как проверяемое свойство

**Проблема.** Адреса с `www` и без `www` были перемешаны в canonical и в JSON-LD, поэтому поисковик видел две разные сущности. Ошибки приходили из данных (ссылки в карточках врачей, фото отделений), а не из кода, поэтому чтение исходников их не находило.

**Решение.** Скрипт собирает приложение отдельно, запускает его и обходит все публичные страницы. Он проверяет:
- единый хост без `www` во всех canonical, JSON-LD, Open Graph и карте сайта;
- что каждый внутренний адрес из JSON-LD открывается;
- что все страницы из списка статических маршрутов отвечают 200 и попадают в sitemap;
- что страницы-перенаправления отвечают 308 на нужный адрес.

Известные нарушения хранились в файле. Когда долг был закрыт, файл опустел: теперь любое найденное нарушение считается новым и роняет проверку. Намеренные отклонения (дубли страниц с canonical на оригинал) объявлены в коде, а не спрятаны в списке исключений.

### 2. Серверные перенаправления вместо клиентских

Раздел, который только пересылал на подстраницу через клиентский код, отдавал роботу 200 и пустое тело. Теперь это серверное перенаправление, а скрипт проверки утверждает код ответа и адрес назначения.

### 3. Деплой, который не ломает работающий сайт

Сборка идёт в отдельную папку и подменяет рабочую, только если завершилась успешно. Любая ошибка после обновления кода (бэкенд не загрузился, сборка, проверка здоровья) возвращает сервер к предыдущему коммиту: зависимости, сборка, процессы. Скрипт отказывается стартовать, если в отслеживаемых файлах есть локальные правки. Поведение отката покрыто тестом, который запускает настоящий скрипт во временном репозитории с подставными `npm`, `pm2` и `curl`.

### 4. Админ-панель: права, сессии, журнал

- Права выдаются по разделам и проверяются на сервере.
- Сессия в httpOnly-cookie, отзывается счётчиком версии: смена пароля или выход закрывают все старые сессии.
- Число попыток входа ограничено. Изменяющие запросы проверяются на допустимый `Origin`.
- Каждый изменяющий маршрут админки обязан записывать действие в журнал, с прежним и новым значением для важных правок. Тест обходит все маршруты и падает, если у нового нет записи. В журнал не попадают тексты обращений и пароли.

### 5. Персональные данные

- IP-адрес клиента нигде не хранится и не пишется в логи в открытом виде, только солёный хеш.
- Идентификаторы в журналах (хеш адреса, сессия) автоматически обнуляются через сутки или 30 дней, в зависимости от журнала. Сами записи остаются: из поисковых запросов получаются данные для SEO.
- Публичные эндпоинты не возвращают адреса получателей писем: получатель определяется на сервере.
- В выгрузках в Excel ячейки, начинающиеся с `=`, `+`, `-`, `@`, экранируются: поле «Врач» заполняет посетитель, и без экранирования оно могло превратиться в формулу.

### 6. Три уровня проверок

- **Без базы данных.** Базу заменяет заглушка, которая отклоняет любой запрос, так что тест не может ничего записать в рабочие данные. Здесь проверяется, что закрытые маршруты закрыты, лимиты на месте, константы фронта и бэкенда не разошлись.
- **В контейнерах.** Настоящие Postgres и Redis, схема взята из дампа рабочей базы, роль приложения с теми же правами, что и в продакшене: запрос, запрещённый там, падает и в тесте.
- **Статические.** Проверка, что все импорты фронтенда разрешаются, и тесты общей логики.

Все три запускаются в CI отдельными заданиями.

## Правила, выведенные из ошибок

- В постраничных запросах к `ORDER BY` всегда добавляется уникальный `id`: без него `LIMIT/OFFSET` повторяет и теряет строки между страницами.
- Метки типов заявок лежат в одном JSON, который читают и фронтенд, и бэкенд. Когда они хранились отдельно, часть заявок выгружалась с сырым английским ключом.
- Несколько записей в базу подряд выполняются только через общую обёртку транзакции с откатом.
- Параметры `limit` и `page` из запроса разбираются в одном месте, и ключ кэша строится из разобранных значений, а не из сырого запроса: иначе одним GET можно раздуть кэш.
